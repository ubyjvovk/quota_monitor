# Stress review — opus — 2026-08-31

## Summary

The Go core is the strongest part of the repo: explicit-path JSON, injected
dependencies, honest `nil`-not-zero window handling, and a cache/config layer
with correct atomic writes and 0600 modes. The damage is concentrated at the
*seams* — between `quotamon`'s exit-code contract and the two frontends that
shell out to it, between the console table and the waybar/widget/panel
transcriptions of it, and between the Swift reference semantics and the Go
port. Two issues are severe enough to make the product silently wrong for a
real user: a normal, expected snapshot (no current windows) is delivered with
exit 1 and therefore thrown away by both the macOS app and the omarchy panel,
and `quotamon config get --json` prints the DeepInfra API key in cleartext
while its human-readable sibling deliberately redacts it. Several
`0%`/staleness-honesty rules the codebase states in its own comments are
violated in the history recorder and the small/medium widget rows. Baseline
tests are green and I changed nothing.

## Findings

### F1 — A valid "nothing current" snapshot exits 1, and both frontends discard it

- file: core/cmd/quotamon/main.go:341
- severity: high   confidence: certain
- claim: `windowExitStatus` returns 1 whenever no provider has a quota window — a normal state — and both consumers of the CLI treat any non-zero exit as a hard failure and drop the JSON that was already on stdout.
- scenario: Every provider's live source is down and its mirror is missing, so `quotamon snapshot` prints a well-formed snapshot whose providers each carry an actionable `status.message` ("Statusline mirror not installed — run install-claude-statusline.sh"), then exits 1 (asserted by `core/cmd/quotamon/main_test.go:95`). `QuotamonRunner.execute` (QuotaKit/Sources/QuotaKit/Engine/QuotamonRunner.swift:135) sees `terminationStatus != 0`, throws `ProcessFailure`, and the panel footer shows `quotamon exited with status 1`; `Panel.qml:137` does the same and shows `quotamon exited 1`. The per-provider guidance never reaches the user. The same happens permanently for a DeepInfra-only setup with no spending limit, which is windows-free but credits-bearing by design (`core/internal/providers/deepinfra/deepinfra.go:107`, and `hybrid.usable` explicitly accepts it).
- fix: either make the CLI exit 0 whenever it emitted a decodable snapshot (reserve non-zero for "could not produce one"), or teach both consumers to parse stdout first and only fall back to the exit code when the JSON is unusable.

### F2 — `quotamon config get --json` prints the API key in cleartext

- file: core/cmd/quotamon/machine.go:69
- severity: high   confidence: certain
- claim: The machine-readable config dump encodes `config.Config` verbatim, including `Provider.APIKey` (`api_key`), while the human-readable branch fifteen lines below deliberately prints only "api key set".
- scenario: A user configures DeepInfra (`quotamon config set deepinfra --api-key=…`), then runs `quotamon config get --json` to check what a frontend sees, or pastes it into a bug report / CI log. The DeepInfra key is emitted in full. The asymmetry with `machine.go:91-93` shows redaction was intended for this command; only the `--json` path forgot. The key is also passed as an argv value at `machine.go:159`, so it is visible to any other user via `ps` and lands in shell history.
- fix: redact `APIKey` in the `--json` encoder (emit `"api_key":"set"` or drop the field) and add a stdin-prompt alternative to `--api-key=`.

### F3 — The macOS app's 15-second process budget is smaller than the CLI's own worst case

- file: QuotaKit/Sources/QuotaKit/Engine/QuotamonRunner.swift:114
- severity: high   confidence: certain
- claim: `QuotamonRunner` kills `quotamon` after 15 s wall clock, but the CLI budgets 25 s for the stale-token phase *plus* 15 s for the fetch (`core/cmd/quotamon/main.go:52-58`), so any run that triggers a Kimi credential refresh is guaranteed to be killed before it can answer.
- scenario: Kimi is enabled and its 15-minute bearer token has expired. `quotamon snapshot` enters `preFetchAll`, `kimi.CLIRefresher.Refresh` launches the TUI with an 8 s startup delay and a 20 s deadline (`core/internal/providers/kimi/refresh.go:93-99`). At t=15 s the app SIGTERMs/SIGKILLs the process and surfaces "quotamon timed out after 15 seconds"; the same command run in a terminal succeeds ~10 s later. The app therefore never shows Kimi quota after a token expiry, and `process.terminate()` does not signal the process group, so the orphaned `script`/`kimi` children keep running.
- fix: raise the runner deadline above `prefetchTimeout + defaultFetchTimeout` (or pass `--timeout` and derive the runner deadline from it), and kill the process group rather than the leader.

### F4 — The Codex HTTP live source silently drops every window's reset time

- file: core/internal/providers/codex/http.go:130
- severity: medium   confidence: certain
- claim: `whamWindow` copies the endpoint's `reset_at` under the key `reset_at`, but `codex.Window` only ever looks for `resets_at`/`resetsAt` (`core/internal/providers/codex/codex.go:45`), so windows built from the wham shape always have `ResetsAt == nil`.
- scenario: A user opts into the HTTP source (`quotamon config set codex --live=http` plus `QUOTA_MONITOR_CODEX_USAGE_URL`). The endpoint returns `rate_limit.primary_window{used_percent:26, limit_window_seconds:18000, reset_at:…}`. The resulting window has no reset, so `Window.CurrentUsedPercent` can never report it as rolled over: a 26% reading from before the window turned over is displayed as current indefinitely, and the countdown column renders `—` instead of a time. The existing test (`core/internal/providers/codex/codex_test.go:207-235`) supplies `reset_at` but never asserts `ResetsAt`, so the gap is invisible to CI. `ClaudeSources.swift:87` and `claude.go:203` both accept `reset_at`, which is what makes this an oversight rather than a decision.
- fix: emit the value under `resets_at` in `whamWindow` (or add `reset_at` to `codex.Window`'s key list) and assert `ResetsAt` in the wham test.

### F5 — `quotamon setup` silently overwrites a config it could not read, destroying the stored API key

- file: core/cmd/quotamon/setup.go:29
- severity: medium   confidence: certain
- claim: Any `config.Load` error other than "missing" — including the deliberate loose-permissions refusal and a JSON syntax error — makes setup start from `config.Default()` and then unconditionally `Save()` over the existing file, with no warning that anything was discarded.
- scenario: The user hand-edits `~/.config/quotamon/config.json` and leaves a trailing comma, or copies it in a way that leaves it mode 0644 (which `config.Load` rejects at `core/internal/config/config.go:76`). They run `quotamon setup --yes` to fix things. Setup cannot read the file, builds a fresh default, finds DeepInfra "not found" because no key is in the environment, and writes a config in which `api_key` is simply gone. The only output is "Wrote …/config.json (mode 0600)". The key is unrecoverable.
- fix: on a non-`ErrMissing` load error, print what went wrong and refuse to overwrite unless the user confirms (or back the old file up to `config.json.bak` before saving).

### F6 — Usage history records 0% for a window that has rolled over

- file: QuotaKit/Sources/QuotaKit/Engine/UsageHistory.swift:41
- severity: medium   confidence: certain
- claim: `record` samples `effectiveUsedPercent`, which returns `0` for a rolled-over window, writing a fabricated "empty window" data point into the sparkline series — precisely what `QuotaWindow.currentUsedPercent`'s doc comment (QuotaKit/Sources/QuotaKit/Models/QuotaWindow.swift:66-71) forbids.
- scenario: Claude's weekly window resets at 14:00. At 14:05 the live fetch fails and the hybrid serves the cached 82% reading taken at 13:50; the window has rolled over, so the table correctly shows `—`, but `record` appends `usedPercent: 0`. The next successful live reading of 4% then draws a series 82 → 0 → 4: a cliff and a rebound the account never experienced. Because the sample is stored, the lie persists after the window is current again.
- fix: use `currentUsedPercent` and skip the sample when it is `nil`; a gap in the series is the honest representation.

### F7 — The reading cache is write-only unless the credential has expired

- file: core/internal/hybrid/provider.go:74
- severity: medium   confidence: certain
- claim: `PreFetch` only loads the cache when `TokenStale != nil && TokenStale(now)`, but `Fetch` saves to it after every usable live reading, so for a provider with no local source a plain transport failure discards a cached reading that is on disk and seconds old.
- scenario: DeepInfra is configured (`Local: nil`, no `TokenStale` — core/internal/registry/registry.go:97-113). A minute after a successful refresh the machine drops off Wi-Fi. `liveOutcome.err != nil`, `localOutcome.attempted == false`, `prepared.cachedOutcome.attempted == false`, so `Fetch` falls through to `snapshot.Unavailable(…, NeedsSetup("Could not reach DeepInfra payment endpoint: …"))`. The panel/table shows "unavailable" and no numbers, even though `~/.config/quotamon/cache/deepinfra.json` holds a 60-second-old balance. Grok has the same shape whenever its token is still valid.
- fix: consult the cache in the fallback chain whenever the live attempt failed, not only on the stale-token path, and label it with its age as `fallbackReading` already does.

### F8 — DeepInfra renders an invoice *count* as a dollar amount

- file: core/internal/providers/deepinfra/deepinfra.go:118
- severity: medium   confidence: certain
- claim: `OverdueInvoices` is documented as "how many unpaid invoices exist" (deepinfra.go:44) and parsed as a count (`int(overdue)` in sources.go:198), but the status message formats it as `$%d`.
- scenario: The `/payment/checklist` response carries `overdue_invoices: 3`. The table and the omarchy panel show `! DeepInfra has $3 in overdue invoices`, telling the user they owe three dollars when they actually have three unpaid invoices of unknown value. Since the same status line is the only overdue signal the tool gives, the user is likely to ignore it.
- fix: `fmt.Sprintf("DeepInfra has %d overdue invoice(s)", …)`, or confirm the field's units against PROVIDERS.md and label it accordingly.

### F9 — One unreadable rollout aborts the whole Codex local read; a chat line can mask a real record

- file: core/internal/providers/codex/local.go:78
- severity: medium   confidence: likely
- claim: A `LastLine` error on any single rollout returns a Transport error for the entire source instead of moving to the next file, and when the last `rate_limits`-containing line in a file is not actually a rate-limits record the loop `continue`s to the *next file* rather than the next line, so the real record earlier in that file is never read.
- scenario: (a) Codex rotates/deletes an old session between `filepath.WalkDir` and `LastLine`'s `os.Stat`; `Fetch` returns "Read Codex session …: no such file or directory" and ChatGPT shows as unavailable even though fifteen other rollouts hold good readings. (b) The user's most recent Codex session ends with an assistant message quoting the token `rate_limits` (e.g. discussing this repo). `LastLine`'s substring match returns that line; `jsonx.Get(root,"payload","rate_limits")` misses; the loop abandons the newest session entirely and reports an older, staler reading — or none.
- fix: treat a per-file error as a skip (record it and continue), and have `LastLine` return candidate lines lazily so the caller can keep scanning backwards within the same file.

### F10 — Small/medium widget rows show a percentage with no origin, age, or status

- file: QuotaKit/Sources/QuotaKit/UI/ConsoleWidgetView.swift:136
- severity: medium   confidence: certain
- claim: `smallLine`/`mediumLine` render short name, bar, percent and countdown only; they carry none of the `live · 4m ago` / `cached` / `!` signals the console header and status lines carry, so a stale cached reading and an errored provider are visually identical to a fresh live one.
- scenario: Claude's live source has been failing for two days and the hybrid keeps serving the statusline mirror with `status = needsSetup("Cached — live refresh failed: …")` and `origin = local`. The systemMedium widget draws `CL ████████░░░░░░░░░░░░ 41%  3d 2h` — indistinguishable from a live 41%. The user believes they have 59% of the week left based on a two-day-old number. `large` is fine because it is `ConsoleTable.render` verbatim.
- fix: reserve a column (or a tone) for non-live origin and non-ok status in the condensed rows — even a single trailing `*` or a dimmed row would restore the distinction.

### F11 — The Waybar tooltip diverges from the table it claims to match

- file: core/cmd/quotamon/waybar.go:65
- severity: medium   confidence: certain
- claim: Three concrete divergences from `renderTableProvider`: the tooltip iterates `provider.Windows` in payload order while the table uses `SortedWindows(now)`; it prints the raw origin string so `local` appears where the table says `cached` (waybar.go:63 vs table.go:177); and it renders credit rows *only* when the provider has no windows (waybar.go:80), while the table renders them whenever `Credits != nil` — despite the comment at waybar.go:81-83 asserting the two never disagree.
- scenario: DeepInfra with a spending limit has both a `monthly_spend` window and a credits block. `quotamon` shows `balance $10.03 remaining` / `spend $7.97 this month`; the Waybar tooltip for the same snapshot omits both lines entirely. For Claude, the tooltip lists `5h`, `Week`, `Fable wk` in payload order while the table leads with the most-constrained window, so the same data reads as a different ranking on two surfaces.
- fix: build the tooltip from `SortedWindows`, reuse `tableOrigin`, and drop the `len(Windows)==0` guard around `creditLines`.

### F12 — Grok's window is hard-labelled "Week" even when the billing period is not a week

- file: core/internal/providers/grok/grok.go:136
- severity: medium   confidence: likely
- claim: `Snapshot` computes `windowMinutes` from the actual `currentPeriod.start/end` (grok.go:108-110) and then discards that information, pinning `Label: "Week"` and `Kind: KindWeekly` — while every other provider derives both from the minutes via `snapshot.LabelFromMinutes`/`KindFromMinutes`.
- scenario: An xAI account whose `currentPeriod.type` is not `USAGE_PERIOD_TYPE_WEEKLY` (the code checks that constant explicitly at grok.go:112, so other values exist) reports a 30-day period. The table prints `Week  ███ 63%  24d 3h` — a "Week" that resets in 24 days — and `TightestWindow`'s kind tie-break ranks a monthly pool above a genuine weekly one from another provider.
- fix: `Label: snapshot.LabelFromMinutes(windowMinutes)`, `Kind: snapshot.KindFromMinutes(windowMinutes)`, keeping "Week" only as the fallback when the period is unknown.

### F13 — Provider short names disagree between the Go and Swift surfaces

- file: QuotaKit/Sources/QuotaKit/Models/ProviderSnapshot.swift:233
- severity: low   confidence: certain
- claim: `ProviderSnapshot.shortNames` maps only Claude and Codex; Grok, DeepInfra and Kimi fall through to `displayName.prefix(2).uppercased()`, producing `GR`/`DE`/`KI`, while `providerShortName` in core/cmd/quotamon/waybar.go:95 defines `GK`/`DI`/`KM` for the same providers.
- scenario: A user runs the Waybar module on Linux and the widget on a Mac against the same account set. The bar reads `GK 63% · DI 12% · KM 40%`; the widget reads `GR 63% · DE 12% · KI 40%`. Nothing is wrong numerically, but the repo's "one derived layer, transcribed" rule is broken in the one place the two surfaces are meant to be quotable against each other.
- fix: move the short-name table into the snapshot contract (or mirror the Go map in `shortNames`) so adding a provider updates both.

### F14 — `discover` execs `security` from `$PATH`, unlike the credential reader

- file: core/internal/discover/discover.go:68
- severity: low   confidence: certain
- claim: The Claude probe runs bare `security`, resolved through `$PATH`, whereas the code that actually reads the token uses the absolute `/usr/bin/security` (core/internal/providers/claude/claude.go:30) precisely to avoid that.
- scenario: A user with a writable directory early on `$PATH` (a Homebrew prefix, `~/bin`, or a compromised project `direnv`) runs `quotamon setup` or `quotamon discover`. The shim named `security` is executed with `find-generic-password -s "Claude Code-credentials"` as its arguments — arguments that tell it exactly which Keychain item to go after — and its exit status decides what the wizard reports. Also, `discoverGrok` (discover.go:99) iterates the credential map in Go's randomised order, so with more than one `https://auth.x.ai::` scope the expiry it reports can belong to a different scope than the one `grok.ParseCredentials` deterministically selects.
- fix: use `/usr/bin/security` here too, and sort the Grok scope keys before reading one.

### F15 — The released `SHA256SUMS` contains a bogus entry for itself

- file: .github/workflows/release.yml:110
- severity: low   confidence: certain
- claim: `(cd dist && shasum -a 256 * > SHA256SUMS)` runs after `scripts/package.sh` has already created `dist/SHA256SUMS`, so the glob includes that file; bash truncates it via the redirection before `shasum` opens it, producing a self-entry that is the SHA-256 of an empty file.
- scenario: A signed release is built. The published `SHA256SUMS` ends with `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855  SHA256SUMS`. A user who downloads everything and runs `shasum -c SHA256SUMS` gets `SHA256SUMS: FAILED` and `1 computed checksum did NOT match` — which, on a security-sensitive verification step, reads as tampering.
- fix: `rm -f SHA256SUMS` before regenerating, or exclude it explicitly (`shasum -a 256 *.dmg quotamon-* > SHA256SUMS`). The same latent problem exists in scripts/package.sh:86 when `<outdir>` is reused.

## What I could not verify

- **I ran no provider end-to-end.** Every source is behind credentials or the
  network, both unavailable here, so all provider findings come from reading
  the code plus the committed fixtures. Specifically I could not confirm the
  live shapes of Kimi's `/usages`, Grok's `/v1/billing`, DeepInfra's
  `/payment/checklist`, or the Codex wham endpoint beyond what
  `QuotaKit/Tests/QuotaKitTests/Fixtures/` and PROVIDERS.md record.
- **F1's exit code was not reproduced by running the binary.** The sandbox
  refused to let me create a scratch `QUOTA_MONITOR_DIR` outside the worktree,
  and I would not write config into the worktree. The claim rests on reading
  `windowExitStatus` (main.go:341-348), its two call sites in `writeSnapshot`,
  and the existing assertions at `core/cmd/quotamon/main_test.go:95` and `:118`,
  which pin the behaviour as intended.
- **F8's units.** I assume `overdue_invoices` is a count, because that is what
  the field name, the `Balance.OverdueInvoices int` doc comment, and the
  `int(overdue)` conversion all say. If DeepInfra actually reports dollars
  there, the `$` is right and the doc comment and type are the bug.
- **F12's premise** that xAI issues non-weekly billing periods. I inferred it
  from the code explicitly comparing against `USAGE_PERIOD_TYPE_WEEKLY`; the
  only fixture is weekly. The internal inconsistency (minutes computed, label
  pinned) holds regardless.
- **F10 and F3 were not observed on screen.** I cannot build or run the macOS
  app or widget on this lane, so the widget/runner findings are read from
  source; I did not render `QUOTA_MONITOR_RENDER` output.
- **The omarchy plugin was not run** — no Quickshell here. `Panel.qml` findings
  are read against the Model.js unit tests that `run-tests.sh` executes.
- I did not audit `docs/`, `.tigerteam/` internals, generated directories, or
  the Swift test suite itself, per the ticket's scope.
- Noted but not filed for space: `hybrid.PreFetch` hard-codes "open `kimi` to
  refresh it" into the refresh-failure message for *any* provider (currently
  safe only because Kimi is the sole provider with a `Refresh` hook);
  `QuotaFormat.accessibleDescription` speaks "0% used" for a rolled-over window
  (QuotaFindings.swift:61) but is currently unreferenced; every hybrid failure
  is reported as `needsSetup`, so the contract's `failed` state is unreachable
  outside DeepInfra suspension; and `Panel.qml`'s `refreshing` flag has no
  watchdog, so a `Process` that never emits `onExited` would latch the Refresh
  button off permanently.

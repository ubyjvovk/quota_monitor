# Stress review — ds — 2026-08-31

## Summary
QuotaMon is in strong shape: the Go core is clean, genuinely table-driven, and the
`quotamon --demo` output is the same byte-for-byte as the Swift `ConsoleTable`
golden that the macOS panel is pinned to — no console-table contract drift.
Error handling is unusually honest (reset windows never render as 0%, staleness is
labelled, live failures are carried into the status). The concerning areas cluster
in the stale-token/cache policy in `internal/hybrid`: the cache is only consulted
for a *stale* token, so a live-only provider loses even a current cached reading on
any ordinary outage, and Kimi's 15-minute token life vs a 5-hour cache window makes
its live endpoint effectively dead between refreshes. Remaining items are lower-risk
(exit-code semantics, a waybar percentage over 100, cosmetic short-name drift).

## Findings

### F1 — Kimi live reading is almost always served from cache, so its live endpoint rarely runs
- file: core/internal/hybrid/provider.go:75-85 (`PreFetch`), core/internal/registry/registry.go:124, core/internal/providers/kimi/kimi.go:5
- severity: medium  confidence: likely
- claim: `PreFetch` short-circuits to the cache (skipping the live source) whenever the token is stale AND the cache is younger than `ShortestWindow` (5h); Kimi's bearer token lives ~15 minutes, so on every refresh the token is almost always stale and a cache under 5h is served.
- scenario: App refreshes every 5min → `quotamon snapshot` runs → Kimi token is stale (>15min old) → a cache reading from, say, 3h ago has a *current* weekly window and is under 5h → it is returned as `ok` and the live `/usages` call never happens. The cache is only re-saved on a real live success, which now can't happen, so Kimi numbers stay frozen at the last real fetch's `observedAt` for up to 5 hours.
- fix: serve a young cache only when it is fresher than the token's practical lifetime (or always attempt live and use the cache only as a fallback), rather than gating on an arbitrary 5h window that dwarfs a 15-minute token.

### F2 — Cache is never consulted on a non-stale live outage; a current reading is dropped for live-only providers
- file: core/internal/hybrid/provider.go:74 (stale gate), 80-85 (cache loaded only inside the stale branch), 144-147 (Fetch cached fallback)
- severity: medium  confidence: likely
- claim: `cachedOutcome` is populated only inside the `if !stale { return }` gate, so when the live token is *not* stale but the endpoint is down, `Fetch` never looks at the cached reading; a live-only provider (Grok, Kimi, DeepInfra have no local) with a perfectly current cached window comes back as `Unavailable`/"No data source configured".
- scenario: token valid, `/v1/billing` returns 500 → live fails, local nil, `cachedOutcome` was never set (line 80-85 only run under the stale gate) → `fallbackReading(prepared.cachedOutcome,...)` (line 145) finds nothing → provider reports `needsSetup` though a current cached reading exists on disk.
- fix: make the cached live reading a fallback on any live+local failure (not only in the stale branch), subject to the same current-window and age checks already used.

### F3 — `windowExitStatus` returns 0 for a snapshot whose windows have all reset
- file: core/cmd/quotamon/main.go:341-346
- severity: low  confidence: likely
- claim: the exit code is 0 whenever *any* provider has ≥1 window, even if every one of those windows has rolled over (so `CurrentUsedPercent` returns nothing and the table renders all dashes).
- scenario: last local readings are from last Tuesday, weekly windows reset Thursday → `quotamon snapshot` prints a table of "—" and exits 0, so a cron/script gating on exit code sees "success" while there is no usable reading.
- fix: base the exit code on whether any window has a *current* reading (or any usable credits reading), not merely that a window object exists.

### F4 — Waybar `percentage` can exceed 100
- file: core/cmd/quotamon/waybar.go:52
- severity: low  confidence: certain
- claim: `int(math.Round(headlinePercent))` is written straight into the Waybar `percentage` field, and `headlinePercent` is not clamped, so an over-limit provider (e.g. 104%) emits percentage 104.
- scenario: a provider reports `usedPercent: 104` → `Percentage: 104` in the payload, which Waybar treats as an out-of-range 0..100 value in some clients.
- fix: clamp `Percentage` to `0..100` (keeping the unbounded value only in Text/tooltip).

### F5 — Short-name catalog drifts between waybar and the menu bar
- file: core/cmd/quotamon/waybar.go:95-106 vs QuotaKit/Sources/QuotaKit/Models/ProviderSnapshot.swift:230-235
- severity: low  confidence: possible
- claim: waybar hard-codes `GK`/`DI`/`KM` for Grok/DeepInfra/Kimi, while the menu-bar `shortNames` map holds only Claude(`CL`) and Codex(`GPT`) and falls back to `displayName.prefix(2)` → `GR`/`DE`/`KI`.
- scenario: once the menu bar renders Grok/DeepInfra/Kimi (the runner already returns all five providers), the tray shows `GR 63% · DE … · KI …` while waybar shows `GK/DI/KM` for the same numbers.
- fix: keep one short-name source (the Go core) and have the Swift `shortNames` fall back to the core's name, or extend the Swift map to the full catalog.

### F6 — `--fresh` is advertised for all commands but rejected for check/setup/providers
- file: core/cmd/quotamon/main.go:31-32 (usage text) vs main.go:320-321 (parseArguments)
- severity: low  confidence: certain
- claim: the usage text shows `quotamon <command> [--demo] [--no-live] [--fresh] …` with no per-command caveat, but `parseArguments` returns invalid (exit 2) for `--fresh` on `check`, `setup`, or `providers`.
- scenario: `quotamon check --fresh` exits 2 with the usage message despite the documented form, which is confusing for a user trying to probe sources past the cache.
- fix: either allow `--fresh` for `check` (or state it is table/snapshot/waybar-only in the usage text).

### F7 — Codex "only after a Codex turn" hint is overwritten by a generic reset message
- file: core/internal/providers/codex/local.go:111-112 vs core/internal/hybrid/provider.go:168-170
- severity: low  confidence: possible
- claim: when Codex's window has rolled over, the local source sets the more actionable `"ChatGPT reports usage only after a Codex turn — last reading …"` status, but the hybrid `fallbackReading` then unconditionally replaces it with the generic `"Last reading …; its window has since reset"` when `len(Windows)>0 && !hasCurrentWindow`.
- scenario: a stale Codex rollout is surfaced as the bland "window has since reset" message, throwing away the clue that running a Codex turn would populate a fresh reading.
- fix: preserve the provider's own status when it is already a `needsSetup` explanation, applying the reset fallback only when the source reported `ok`.

### F8 — Grok cached reading can be served as `ok` up to 7 days old
- file: core/internal/registry/registry.go:91-93, core/internal/hybrid/provider.go:75-85
- severity: low  confidence: possible
- claim: Grok's `ShortestWindow` is 7×24h and its single window is weekly, so a cached billing reading under a week old with a still-unreset window is served as `ok` without touching the live endpoint.
- scenario: user signs out of Grok / network is down; a 6-day-old cached reading where the weekly window has not yet rolled is served as current `ok`, even though promo/plan changes would be hidden for up to a week.
- fix: tighten the stale-serving window (or the age at which a staleness status is attached) rather than allowing a week-long silent cache.

### F9 — Waybar tooltip lists windows in provider order, not sorted order
- file: core/cmd/quotamon/waybar.go:41-50 (providerTooltip iterates `provider.Windows`)
- severity: low  confidence: possible
- claim: the tooltip renders windows in the snapshot's raw slice order while the table uses `SortedWindows` (most-constrained first), so the two surfaces disagree on which window is presented first.
- scenario: a provider reports `[weekly 40%, session 90%]` in that order → the tooltip leads with "Week 40%" while the table leads with "5h 90%", inviting a misread of the most constrained window.
- fix: iterate `provider.SortedWindows(now)` (or `TightestWindow` first) in the tooltip to match the table.

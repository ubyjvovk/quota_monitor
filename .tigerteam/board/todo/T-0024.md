## Goal
`quotamon setup` wrote `"kimi": {"enabled": false}` while Kimi was still
unsupported (from `config.Default()`), and `setup --yes` treats an on-disk
value as the user's choice. Result on the reference machine: after Kimi
became supported, `setup --yes` reported `✓ Kimi … found` yet left it off,
and the table never showed it. Non-interactive setup must be able to adopt
a newly supported, found provider.

## Design — implement exactly this
- `config.Default()` returns an **empty** providers map (no entries).
- `setup` writes entries **only** for supported providers, and only those the
  user decided on (interactive: every supported provider is asked, so all
  get entries; `--yes`: entries for found providers = enabled, and for
  not-found providers = disabled). Unsupported providers never get an entry.
- `--yes` rule becomes: `enabled = found || (entry exists && entry.Enabled)`
  — an existing `false` entry for a **found** provider is overridden to
  `true` only when the entry was never explicitly chosen… since that cannot
  be known, adopt the simpler, documented rule: **`--yes` enables every
  found supported provider and keeps keys**; users who want a found provider
  off run interactive setup or edit the file (say so in the `--yes` output:
  `Enabled every provider that was found; run without --yes to choose.`).
- Loading a config that has an entry for an unknown/unsupported id must not
  fail (ignore it); the registry already omits unknown ids — verify.

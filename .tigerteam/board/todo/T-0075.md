## Goal
Two related defects in the plugin's update story.

**1. The panel diagnoses a stale core and then abandons the user.**
`Model.versionWarning` already detects a core older than the manifest's minimum
and renders, in red: *"quotamon 2026.9.1 is older than this plugin needs
(2026.9.2) — update it and press Refresh"*. There is no way to update it from
the panel. The Install button exists but is `visible: root.rows.length === 0`,
so it appears only when there are no readings at all — precisely not the case
when an old-but-working core is reporting numbers. The advice is a dead end
that ends at a terminal.

**2. The installer is not pinned, though everyone assumes it is.**

```bash
release_base=${QUOTAMON_RELEASE_BASE:-https://github.com/ubyjvovk/quota_monitor/releases/latest/download}
```

That is `latest`, verified against the `SHA256SUMS` published *in that same
release*. It detects a corrupted or substituted download, which is worth having,
but it pins nothing: the panel installs whatever is newest, including a core the
plugin has never been tested against. The plugin should install the core version
it was built with.

No periodic version check is being added, and none is needed — see Context.

## Context
- The panel already knows both versions on every refresh, with no extra work:
  - the running core, from the snapshot's top-level `version` key (T-0064),
    read by `Model.coreVersion(snapshot)`;
  - the version it expects, from its own `manifest.json`, read once over
    `XMLHttpRequest` and parsed by `Model.parseManifest` into
    `{ version, minQuotamon }`.
  The plugin and the core ship from one `VERSION` file in one release, so
  `manifest.version > core version` already means "a newer core exists". This
  is a local comparison; **do not add any network call, timer or GitHub API
  request.** (Owner's decision, 2026-09-01, chosen over polling the releases
  API precisely to avoid a second failure mode and a new trust surface in a bar
  widget.)
- `Panel.qml` already has everything else needed:
  - `root.installScript` — `Qt.resolvedUrl("fetch-quotamon.sh")` decoded to a
    filesystem path, anchored to the QML file rather than the shell's cwd;
  - `installQuotamon()` — argv execution (`["bash", root.installScript]`, no
    shell, no interpolation), with a 30 s watchdog;
  - `installProc.onExited` — already calls `root.refreshNow(true)` on exit code
    0, so the footer updates itself after a successful install. **That part is
    done; do not re-implement it.**
- `fetch-quotamon.sh` is already an *install or update* script: it stages the
  binary on the destination filesystem and `mv -f`s it over any existing one.
  Only its URL needs a version.
- **The two version fields answer different questions. Do not merge them.**
  - `manifest.version` — the core version this plugin ships with. Rewritten
    automatically by `scripts/set-version.sh`, which touches only the top-level
    `"version"` key. It drives the **update offer**: "a newer one exists".
  - `manifest.dependencies.quotamon` (`minQuotamon`) — the oldest core the
    plugin can actually work with. `set-version.sh` does **not** touch it and
    neither does `check-versions.sh`; it is hand-edited, and only when the
    plugin genuinely starts needing something newer. It drives the red
    **warning**: "too old to work".
  This split is what makes the common case behave. Adding a provider to the Go
  core changes nothing the plugin needs — the panel is a dumb renderer of
  whatever providers the snapshot contains — so a providers-only release bumps
  `manifest.version` while `minQuotamon` stays put, and the user gets a quiet
  *offer* rather than a red *warning*. Both can still be true at once when the
  plugin really does need a newer core. Keep them as separate functions and keep
  `coreUpdateVersion` away from `minQuotamon`.
- **The QML cannot run on this host.** Follow the pattern T-0067 established:
  every decision lives in `Model.js` behind `model_test.mjs`, and `Panel.qml`
  only binds to it. A reviewer can run the node tests; nobody here can run the
  panel.

## Design (decided; implement exactly this)

**1. `fetch-quotamon.sh` accepts an optional version**

```
usage: fetch-quotamon.sh [<version>]
```

- With a version, the release base becomes
  `https://github.com/ubyjvovk/quota_monitor/releases/download/v<version>`.
  Without one, keep today's `latest/download` — by-hand use keeps working.
- **Validate before use.** The value is interpolated into a URL, so reject
  anything that is not CalVer with the same regex the repo already uses:
  `^[0-9]{4}\.(1[0-2]|[1-9])\.[0-9]+$`. On a bad value, print
  `usage: fetch-quotamon.sh [<version>]` to stderr and exit 2 — before any
  network call, any temp directory, and any write.
- More than one argument is also exit 2.
- An explicit `QUOTAMON_RELEASE_BASE` still wins over both, unchanged; the
  existing `QUOTAMON_ARCH` / `QUOTAMON_BIN_DIR` overrides are untouched.
- Immediately before the first `curl`, print one line to stdout:
  `Fetching quotamon <version-or-"latest"> from <resolved release base>`
  It is genuine UX — the panel surfaces this script's output when it fails —
  and it is how the acceptance criteria below verify the URL without a network.
- Everything after the URL — the architecture mapping, the isolated temp
  download, the `SHA256SUMS` check of the exact asset name, the staged atomic
  `mv -f`, the exit-3 `setup --yes` bootstrap, the PATH advice — stays exactly
  as it is. Do not restructure this script.

**2. `Model.js` — two small pure functions, no I/O**

```js
// The version to install: the manifest's own version when it is valid CalVer,
// else "" (the panel then omits the argument and the script falls back to latest).
function pinnedVersion(manifest)

// The version to offer as an update, or "" when none should be offered.
function coreUpdateVersion(manifest, snapshot)
```

- `pinnedVersion` returns `manifest.version` only if it matches the CalVer
  regex above; otherwise `""`. A malformed manifest must never reach argv.
- `coreUpdateVersion` returns `pinnedVersion(manifest)` when **all** hold:
  `pinnedVersion(manifest)` is non-empty; `coreVersion(snapshot)` is non-empty;
  and `compareVersions(core, manifestVersion) < 0`. Otherwise `""`.
  Reuse the existing `compareVersions` — it is already numeric per component,
  which is why `2026.10.1` correctly beats `2026.9.9`. A `null` comparison
  (unparseable) means **no** offer.
- An unknown core version (`""`, e.g. a core too old to report one) must **not**
  produce an update offer here; that case is what `versionWarning` is for.
- Change `versionWarning`'s trailing advice from
  `— update it and press Refresh` to `— use the Update button below`, in both
  of its return paths. Nothing else about it changes.

**3. `Panel.qml` — pass the version, add the button**

- `installQuotamon()` builds argv from the manifest itself, so both buttons call
  it identically and neither can pass something different:

```js
var command = ["bash", root.installScript]
var pinned = Model.pinnedVersion(root.manifest)
if (pinned !== "")
    command.push(pinned)
installProc.command = command
```

  Still argv, still no shell.
- Add one `Button` immediately after the `versionWarning` `Text` block (around
  line 433), mirroring the existing Install button's properties
  (`iconText: "󰇚"`, `iconSpinning`, `bordered`, `foreground`, `fontFamily`):
  - `visible: Model.coreUpdateVersion(root.manifest, root.snapshot) !== ""`
  - `text: installProc.running ? "Updating…" : "Update quotamon to " + Model.coreUpdateVersion(root.manifest, root.snapshot)`
  - `enabled: !installProc.running`
  - `onClicked: root.installQuotamon()`
- Leave the existing Install button, its `visible: root.rows.length === 0`
  condition, the Refresh button, `installProc`, and the watchdog untouched.

**4. `omarchy/README.md`**

Document, briefly: the panel offers an Update button when the installed core is
older than the plugin; the plugin installs the exact core version it ships with
rather than whatever is newest; and nothing is ever installed or updated
automatically — a person clicks. Fold this into the existing Install section
rather than starting a new one.

## Out of scope
- Any periodic or background version check, any GitHub API use, any new `Timer`.
  This was decided against deliberately.
- Automatic install or update. The script runs only when a person clicks;
  `omarchy/README.md` says so and must keep saying so.
- Restructuring `fetch-quotamon.sh` beyond the version argument, its validation,
  and the one echoed line. The download isolation, checksum verification and
  atomic install are correct — leave them alone.
- `core/`, the release workflows, `scripts/`, `VERSION`, or the manifest's
  `version` / `dependencies` values.
- The Install button's `visible` condition, the Refresh button, the watchdog,
  and `installProc.onExited` (which already re-reads the version on success).
- Bumping any version to make the update button appear during testing. Prove the
  behaviour in `model_test.mjs` with constructed inputs instead.

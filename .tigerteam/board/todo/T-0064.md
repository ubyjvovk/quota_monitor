## Goal
Give the project one machine-readable version string and make the Go core the
first component to carry it. Today nothing reports a version: `quotamon` has no
`--version` flag, and the snapshot JSON its two GUI frontends consume carries no
version at all, so neither the macOS app nor the Omarchy plugin can say which
core it is talking to. This ticket creates the single source of truth
(`VERSION` at the repo root), stamps it into the binary at build time, and
exposes it two ways: a `--version` flag and a top-level `version` key in the
snapshot contract.

The version scheme is **CalVer `YYYY.M.MICRO`** — year, month (no zero
padding), and the count of releases within that month starting at 1. The first
release is `2026.9.1`; a second release in September 2026 would be `2026.9.2`;
the first in October 2026 would be `2026.10.1`. MICRO is **not** the day of the
month. (PM decision 2026-09-01, confirmed by the owner.)

## Context
- `core/go.mod` declares module `quotamon`, so an ldflags path looks like
  `-X quotamon/internal/version.Value=...`.
- `core/Makefile` has three targets. `build` produces `bin/quotamon`; `matrix`
  cross-builds the four release binaries and already passes
  `-ldflags="-s -w"` — merge, do not duplicate, the `-ldflags` argument.
- `project.yml` (macOS app, out of scope here) runs `make -C core matrix` as an
  Xcode pre-build phase and lipos the darwin slices into the app bundle. That
  is why the stamp must live in the Makefile: it is the only path by which the
  app's bundled core gets a version.
- Argument handling lives in `core/cmd/quotamon/main.go`. `runWithDependencies`
  begins with a loop over every argument that answers `--help`/`-h` before any
  command parsing — `--version` belongs in that same loop so it works in any
  argv position and for any subcommand. `parseArguments` has a second identical
  `--help` loop; check whether it needs the same treatment for the flag to be
  accepted rather than rejected as unknown.
- `usageText` (top of `main.go`) is the CLI's own documentation and is the
  documentation deliverable for this ticket. Some tests pin it; update them.
- The snapshot contract is `core/internal/snapshot/snapshot.go`. `Snapshot` has
  a **custom `MarshalJSON`** that re-wraps the struct through a `snapshotJSON`
  alias plus an anonymous struct to force `providers` to encode as an array —
  a new field must survive that path, so assert on real marshalled JSON, not
  on the struct.
- Snapshots are assembled in exactly two places: `core/cmd/quotamon/main.go`
  (~line 374) and `core/cmd/quotamon/demo.go` (~line 22). Both must stamp the
  version, so `--demo` output is as honest as a live run.
- Consumers of this JSON are `QuotaKit` (Swift `QuotaSnapshot`) and
  `omarchy/Model.js`. Both ignore unknown keys, so adding `version` is
  backward compatible and **neither is in scope here**.

## Design (decided — implement exactly this, do not redesign)
1. `VERSION` at the repo root contains exactly `2026.9.1` and a trailing
   newline. Nothing else in the file.
2. New package `core/internal/version` (file `version.go`):
   ```go
   // Package version carries the CalVer release string stamped into the binary
   // at build time.
   package version

   // Value is the release this binary was built from, in CalVer YYYY.M.MICRO
   // form. It defaults to "dev" and is overwritten at link time by
   // core/Makefile with the contents of the repo-root VERSION file, so a
   // `go build ./...` with no ldflags is honestly labelled rather than
   // falsely stamped.
   var Value = "dev"
   ```
3. `core/Makefile` resolves `VERSION := $(shell cat ../VERSION 2>/dev/null || echo dev)`
   and passes `-ldflags "-X quotamon/internal/version.Value=$(VERSION)"` in
   `build`, and `-ldflags "-s -w -X quotamon/internal/version.Value=$(VERSION)"`
   in `matrix` (one `-ldflags` per invocation).
4. `quotamon --version` prints exactly `quotamon <Value>` followed by a newline
   to **stdout** and exits 0 — e.g. `quotamon 2026.9.1`, or `quotamon dev` for
   an unstamped build. It is handled alongside `--help`, before command
   dispatch, so `quotamon --version`, `quotamon snapshot --version` and
   `quotamon --demo --version` all work. There is no `-V` short form and no
   `version` subcommand.
5. `usageText` gains, in the Options block, aligned with the existing columns:
   `  --version                 Print the quotamon version and exit`
6. `snapshot.Snapshot` gains a `Version string` field with tag
   `json:"version,omitempty"`, documented in the same comment style as the
   neighbouring fields ("Version is the quotamon release that produced this
   snapshot."). Field order: `Version` first, then `Providers`, then
   `GeneratedAt`; the JSON key order does not matter.
7. Both assembly sites set `Version: version.Value`.

      file is committed
- [ ] `cd core && go build ./... ` then running the binary with `--version`
      prints `quotamon dev`; `make -C core build && ./core/bin/quotamon --version`
      prints `quotamon 2026.9.1`. Record both outputs verbatim in the Worker
      report.
- [ ] `make -C core matrix` still succeeds and its binaries are stamped:
      `strings core/bin/quotamon-linux-amd64 | grep -c 2026.9.1` is non-zero
      (or equivalent evidence). Record the command used.
- [ ] New Go tests cover, at minimum: (a) `--version` writes `quotamon dev`
      to stdout and returns exit code 0 with the package default; (b)
      `--version` still works when a subcommand is present (e.g.
      `snapshot --version`); (c) marshalling a `Snapshot` with a version
      produces a top-level `"version"` key with that value **through the
      custom MarshalJSON**; (d) a `Snapshot` with an empty version omits the
      key entirely.
- [ ] `quotamon snapshot --demo` and `quotamon --json --demo` both emit a
      top-level `"version"` key. Paste one of them (first 3 lines is enough)
      into the Worker report.
- [ ] `quotamon --help` shows the `--version` line, and any test pinning the
      usage text is updated to match
- [ ] `go vet ./...` clean (run-tests.sh covers this)
- [ ] No files changed outside scope

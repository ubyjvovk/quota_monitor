## Goal
When a live source fails and the cached fallback's window has since rolled
over, `fallbackReading` overwrites the status with a sentence about the cache
and **returns before it ever looks at the live error**:

```go
if provider.Status.State == "ok" && len(provider.Windows) > 0 && !hasCurrentWindow(provider, asOf) {
    provider.Status = snapshot.NeedsSetup(
        "Last reading " + format.Age(asOf.Sub(provider.ObservedAt.Time)) + "; its window has since reset",
    )
    return provider, true          // <- liveError is dropped on the floor
}
```

So the user is told *when the cache was taken* and never *why the live read
failed*. On 2026-09-01 this cost real time: Grok showed "Last reading 4h ago;
its window has since reset" on two machines, which reads as a refresh or token
problem. The actual live error was `Unrecognised response from Grok billing
endpoint` (fixed under T-0071) — the one sentence that would have pointed
straight at the parser, and the only one the user never saw.

`PROVIDERS.md` states the rule this violates: *"Report failures the user can
act on. 'Run `grok login`' beats a status."* A stale-window note is a status. A
live error is usually actionable.

## Context
- `fallbackReading(candidate, asOf, refreshMessage, liveError, cached)` in
  `core/internal/hybrid/provider.go` is reached from two call sites: the local
  fallback (`cached=false`) and the cached fallback (`cached=true`).
- Its later branches already know how to fold a reason in, and the `cached`
  form has `cachedFallbackMessage` to prefix `Cached <age> — `. The
  window-reset branch is simply an earlier `return` that skips all of it.
- Precedence today, once the reset branch is passed: `refreshMessage` wins over
  `liveError`. Keep that ordering.
- A second, smaller defect in the same file — `PreFetch`:

```go
prepared.refreshMessage = fmt.Sprintf("%s sign-in is stale — open `kimi` to refresh it (auto-refresh failed: %v)", p.DisplayName, err)
```

  The provider name is interpolated but the remedy is hardcoded to `kimi`. It
  is correct only because Kimi is the sole provider wired with a `Refresh`
  today (`registry.go:129`); the next provider to get one inherits a message
  telling its user to open the wrong CLI.

## Design (decided; implement exactly this)

**1. The window-reset branch must carry the reason.**

Keep the existing sentence — it is genuinely useful, it explains why a number
is not being shown — and append the reason when there is one, choosing it with
the precedence already used below (`refreshMessage`, else `liveError`):

- with a reason:
  `Last reading 4h ago; its window has since reset — live refresh failed: <reason>`
- with no reason (both empty): exactly today's sentence, unchanged.

Use the same `live refresh failed: ` wording the `liveError` branch below
already uses, so the vocabulary stays consistent. When the reason is a
`refreshMessage`, append it without that prefix — it is already a full
sentence.

Do **not** apply `cachedFallbackMessage`'s `Cached <age> — ` prefix here: this
sentence already opens with the age, and prefixing would state it twice.

**2. `PreFetch`'s refresh-failure message must name the provider's own CLI.**

Replace the hardcoded `kimi` with the provider's remedy. Add one field to
`Provider`:

```go
// RefreshHint names the command a user runs to renew this provider's
// credential by hand, e.g. "kimi". Empty means no hint is offered.
RefreshHint string
```

Message with a hint (identical to today's text for Kimi once
`RefreshHint: "kimi"` is set in the registry — verify that byte-for-byte):

```
<DisplayName> sign-in is stale — open `<RefreshHint>` to refresh it (auto-refresh failed: <err>)
```

Without a hint:

```
<DisplayName> sign-in is stale and could not be refreshed automatically: <err>
```

Setting `RefreshHint` in the registry is **out of scope** — see below. The
field ships unset, which is why the no-hint wording must be correct on its own.

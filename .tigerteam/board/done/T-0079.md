## Goal
Today the expected checksum travels with the binary:

```bash
curl -fsSL "$release_base/$asset"     -o "$tmp_dir/$asset"
curl -fsSL "$release_base/SHA256SUMS" -o "$tmp_dir/SHA256SUMS"
```

Both come from the same GitHub release, so whoever controls the release
controls both. That detects a corrupted or substituted *download* and proves
nothing about a compromised *release*. A security review of the published
plugin (commit `7aa3d8e`) called this out; T-0078 fixed the review's other point
(an environment override outranking the pin). This ticket fixes this one.

The plugin will carry, in reviewed code, the SHA-256 of the exact core binaries
it was released with. The installer verifies against **that**, not against a
file it just downloaded. A swapped release asset then fails the check, and an
attacker would also have to push to the plugin repository — which leaves a
commit in git history where a human sees it.

**Honest limit, so nobody oversells it:** both repositories live under one
GitHub account. This raises the bar; it does not survive an account compromise.
That would need a signature with a key that is not on GitHub, or build
attestations, and is a separate decision. Do not add either here.

## Context — read before designing anything
- The checksums **do not exist until after the tag**: `release.sh` pushes
  `v<VERSION>`, which triggers the macOS build that produces the binaries and
  `SHA256SUMS`. So a digest cannot be committed alongside the version bump. It
  is written in a step that runs *after* the main release exists and *before*
  the plugin is published. That ordering already happens by hand today — the
  panel's Update button downloads from `releases/download/v<version>/`, so the
  plugin is always published after the release is built. This ticket makes the
  ordering enforced instead of remembered.
- **Where the digest lives is decided: a sidecar file, not the manifest.**
  `omarchy/quotamon-<version>.sha256`, in the exact format `shasum -c` consumes:
  ```
  <64 hex>  quotamon-linux-amd64
  <64 hex>  quotamon-linux-arm64
  ```
  Reasons, so they are not relitigated: the verifier is bash, and `jq` is not
  among the plugin's declared `commands: ["curl", "shasum"]`; a digest in the
  manifest could only be enforced by the panel passing it via argv, which means
  by-hand runs get no check — the script must hold the line on its own; and
  putting the version in the **filename** lets the script decide "pinned or
  not" by existence alone, with no parsing.
- `fetch-quotamon.sh` resolves its own directory the same way `Panel.qml`
  resolves the script: `$(dirname "${BASH_SOURCE[0]}")`. The sidecar sits
  beside it in the installed plugin.
- The current verification block (the `grep -E "^[[:xdigit:]]{64}..."` line,
  the `shasum -a 256 -c -` subshell, and the "missing checksum is as unsafe as
  a mismatch" comment) is correct and stays — it just reads from a different
  file when a sidecar exists.
- The panel passes the manifest version (T-0075) and refuses an environment
  override alongside it (T-0078). Nothing in `Panel.qml` or `Model.js` changes
  here; **do not touch them.**
- `scripts/publish-omarchy-plugin.sh` already gates on `check-versions.sh` and
  reports tag state. It is the right place for the new gate. `check-versions.sh`
  is **not**: it runs inside the test suite, and between `set-version.sh` and
  the build finishing the sidecar *cannot* exist yet — that window is the
  release ritual, and a red suite there would be noise.
- `omarchy/.github/workflows/release.yml` already has a "Verify tagged version"
  step and, from T-0076, a best-effort fetch of the core release. Model the new
  step on those.

## Design (decided; implement exactly this)

**1. `scripts/pin-quotamon-digest.sh` (new)**

```
usage: scripts/pin-quotamon-digest.sh            pin the digests for $(cat VERSION)
```

- Resolves `ROOT` like `scripts/build.sh` does and reads `VERSION`.
- Downloads `https://github.com/ubyjvovk/quota_monitor/releases/download/v<VERSION>/SHA256SUMS`
  to a temp file with `curl -fsSL`. On failure: print
  `release v<VERSION> has no SHA256SUMS yet — run scripts/release.sh and wait for the build`
  to stderr, exit 1, write nothing.
- Extracts exactly the two lines for `quotamon-linux-amd64` and
  `quotamon-linux-arm64`, using the same strict pattern the installer uses
  (`^[[:xdigit:]]{64}[[:space:]]+\*?<asset>$`). If either is missing, exit 1
  and write nothing — a half-pin is worse than none.
- Deletes every existing `omarchy/quotamon-*.sha256`, then writes
  `omarchy/quotamon-<VERSION>.sha256` with the two lines, asset name **without**
  a leading `*`. Exactly one sidecar exists after a run.
- Prints the two lines it wrote. Does **not** commit; the maintainer reviews the
  two-line diff and commits — that review is the point.

**2. `omarchy/fetch-quotamon.sh`**

After the existing argument and override validation, and before any download:

```bash
script_dir=$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)
pin_file=""
if [[ -n $version ]]; then
  pin_file="$script_dir/quotamon-$version.sha256"
  if [[ ! -f $pin_file ]]; then
    echo "refusing to install: this plugin carries no digest for quotamon $version ($pin_file)" >&2
    echo "the plugin and the core version must match; update the plugin, or run without a version to install latest unverified-by-pin" >&2
    exit 2
  fi
fi
```

Then, in the download block:
- With a pin file: download **only** the asset. Do not fetch `SHA256SUMS` from
  the release at all — in the threat model where the release is compromised,
  that file is attacker-controlled and adds nothing. Verify the asset against
  `$pin_file` using the existing grep + `shasum -c` block, pointed at the
  sidecar.
- Without a pin file (no version given): today's behaviour, unchanged — fetch
  `SHA256SUMS` from the release and verify against it — plus one line to
  stdout before the download: `warning: installing latest without a plugin
  digest pin; the checksum comes from the same release as the binary`.
- The `Fetching quotamon … from …` line from T-0075 stays; append ` (pinned)`
  when a sidecar is in use.
- Update the header comment: the script verifies against the digest the plugin
  shipped with when a version is given.

**3. `scripts/publish-omarchy-plugin.sh`**

After the `check-versions.sh` gate and before the subtree split, add a gate:

- `omarchy/quotamon-$(cat VERSION).sha256` must exist, else:
  `Refusing to publish: no digest pin for <VERSION> (run scripts/pin-quotamon-digest.sh after the release builds)` → exit 1.
- Exactly one `omarchy/quotamon-*.sha256` may exist, else refuse naming the
  extras.
- Fetch the live release's `SHA256SUMS` for `v<VERSION>` and confirm both
  pinned lines appear in it verbatim (modulo a leading `*` on the asset). A
  mismatch means either a stale pin or a tampered release — refuse either way:
  `Refusing to publish: pinned digest for <asset> does not match release v<VERSION>`.
  If the release cannot be reached, refuse: the publish must not proceed on an
  unverifiable pin. (`--dry-run` performs the same checks and reports; it still
  pushes nothing.)
- Print `Digest pin: quotamon-<VERSION>.sha256 verified against release v<VERSION>`
  in the summary block, before the tag line.

**4. `omarchy/.github/workflows/release.yml`** — second line of defense

A new step after "Verify tagged version", `if: github.event_name == 'push'`,
named "Verify digest pin":
- `quotamon-${VERSION}.sha256` must exist in the checkout.
- Fetch `https://github.com/ubyjvovk/quota_monitor/releases/download/v${VERSION}/SHA256SUMS`
  and confirm both pinned lines appear verbatim. **This one fails the job on any
  problem** — unlike T-0076's notes fetch, a plugin release with an unverifiable
  pin must not be cut. The publish script already guarantees ordering, so the
  release will exist; if it does not, failing is the correct outcome.
- The zip already excludes nothing relevant; confirm the sidecar **is** included
  in the zip (it must ship with the plugin) and say so in the report.

**5. Docs**

- `omarchy/README.md`, Install section: one paragraph — the plugin ships the
  SHA-256 of the core version it was released with, the Update/Install buttons
  verify against that rather than against a checksum downloaded beside the
  binary, and a plugin/core version mismatch is refused rather than guessed.
  Keep the existing "nothing is ever installed automatically" sentence.
- `README.md`, the release sequence bullet (the one T-0070 wrote): the sequence
  becomes `set-version.sh` → commit → `release.sh` → *wait for the build* →
  `pin-quotamon-digest.sh` → commit → `publish-omarchy-plugin.sh`, and say that
  the publish refuses without a verified pin.

## Goal
Grok is frozen on a stale cached reading on every machine the owner runs, and
clicking Refresh cannot clear it. The PM reproduced and proved the cause on
2026-09-01; it is **not** a token, network or refresh problem.

`Snapshot` in `grok.go` rejects the whole response when `creditUsagePercent` is
missing:

```go
usedValue, ok := jsonx.Get(config, "creditUsagePercent")
if !ok {
    return snapshot.Provider{}, false   // -> "Unrecognised response from Grok billing endpoint"
}
```

The live endpoint currently returns **HTTP 200 with that field absent**. The
weekly period reset at `2026-09-01T11:09:21Z` and usage since then rounds to
zero, so the field — and `productUsage` — are simply not serialised (the API is
protobuf-JSON shaped: `USAGE_PERIOD_TYPE_WEEKLY`, `{"val": 0}` wrappers; a
plain scalar at its default and an empty repeated field are both omitted, while
an explicitly-set wrapper message still emits `"val": 0`).

So every live fetch is judged malformed, hybrid falls back to the cache, and
the user sees a reading taken minutes before the reset — at 100% — with the
message "Last reading 4h ago; its window has since reset". Grok will unfreeze
by itself only once usage climbs back over ~1%, then freeze again after the
next weekly reset. **A quota tool must be able to say "you have used none of
it".**

  products. That shape is still valid when usage is non-zero; it is not wrong,
  it is incomplete.

## Design (decided; implement exactly this)

In `Snapshot`, keep every behaviour for a response that **has**
`creditUsagePercent` byte-for-byte identical. Only the absent case changes.

1. `config` missing → return false, as today.
2. `creditUsagePercent` present:
   - numeric → `usedPercent` is that value; continue exactly as today.
   - present but not numeric → return false, as today.
3. `creditUsagePercent` **absent** → do not reject. Instead:
   - Require a recognisable envelope, so a foreign or error body is still
     refused: at least one of `currentPeriod.start`/`currentPeriod.end` must
     parse as a time, **or** `currentPeriod.type` must be a non-empty string.
     If none of those hold, return false.
   - Derive the percentage:
     - if `productUsage` is a non-empty array, sum every element's numeric
       `usagePercent` (PROVIDERS.md records that the products are a breakdown
       of one shared pool: 57 + 5 + 1 ≈ 63), and clamp the total to `[0, 100]`;
     - otherwise `usedPercent = 0`.
   - Everything downstream — period bounds, label, kind, `windowMinutes`,
     `resetsAt`, `prepaidBalance` credits, `Status: OK()` — is computed by the
     code that already exists, unchanged.

The `productUsage` branch is defensive: the two fields are expected to vanish
together. Implement it anyway — it costs a few lines and it is the difference
between "we assumed zero" and "we read what was there".

Add a comment at the branch saying *why* absence means zero, citing the
protobuf-JSON default-omission behaviour, so nobody later "fixes" it back into
a rejection.

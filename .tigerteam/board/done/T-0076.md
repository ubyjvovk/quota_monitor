## Goal
The plugin repository's release notes are `generate_release_notes: true`, which
builds them from **that repository's** commits. The plugin's history is a
subtree split of `omarchy/`, so a release cut for a core-only change — a new
provider, a bug fix in `core/` — contains exactly one commit: the
`manifest.json` version bump that `scripts/set-version.sh` wrote.

The result is a release page that says a number changed and nothing about why
anyone would want it. With T-0075 the panel now offers "Update quotamon to
2026.9.3" and a curious user clicking through to the release learns nothing.
The plugin's release should carry the core's news.

## Context
- The two repositories release in lockstep from one `VERSION`: `release.sh`
  pushes `v<VERSION>` to `quota_monitor`, and `publish-omarchy-plugin.sh`
  pushes the same tag name to `quotamon-omarchy`. So for any plugin tag `vX`
  there is a main-repo release with the identical tag.
- **Ordering hazard, and the reason this needs a fallback.** The main release is
  built by `.github/workflows/release.yml` on a `macos-15` runner — it compiles
  a universal app, packages a DMG, and may notarize. That takes minutes. The
  maintainer runs `publish-omarchy-plugin.sh` right after `release.sh`, so the
  plugin's workflow can easily start **before the main release exists**. A
  lookup that assumes it is there will 404 and must not fail the release.
- The workflow already has `permissions: contents: write` and the automatic
  `GITHUB_TOKEN`. Both repositories are public and owned by the same account,
  so a cross-repo read of a release works; authenticate the call anyway, because
  unauthenticated api.github.com calls from Actions runners share a heavily
  rate-limited IP pool.
- `softprops/action-gh-release@v2` accepts `body` and `generate_release_notes`
  together: the generated commit list is appended below the supplied body. Keep
  both — the body carries the core's news, the generated part keeps the plugin's
  own commit history visible.
- **You cannot run GitHub Actions here.** The acceptance criteria below are
  built so the body-building logic is exercised by hand instead; that is why
  the design splits fetching from formatting.

## Design (decided; implement exactly this)

Two new steps in `omarchy/.github/workflows/release.yml`, both before the
existing "Publish release" step and both `if: github.event_name == 'push'`.

**Step A — "Fetch core release notes" (best effort, never fails the job)**

```bash
api=${GH_API_BASE:-https://api.github.com}
curl -fsSL \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github+json" \
  "$api/repos/ubyjvovk/quota_monitor/releases/tags/$GITHUB_REF_NAME" \
  -o core-release.json || rm -f core-release.json
```

- `GITHUB_TOKEN` comes from `env:` on the step, not interpolated into the
  script body.
- The `|| rm -f` is the whole error policy: on any failure the file is simply
  absent and Step B handles it. **Do not add `continue-on-error`, and do not let
  a missing core release fail the job** — the plugin release is still correct
  and useful without the notes.

**Step B — "Build release body" (pure formatting, no network)**

Reads `core-release.json` if it exists and writes `release-body.md`. Extract the
core release's `body` field. Do not assume `jq` parses it into something safe to
`echo` — use `jq -r '.body // ""'` (jq is present on `ubuntu-latest`) and write
it with a heredoc or `printf '%s'`, never by interpolating it into a command.

With the file present and a non-empty body:

```markdown
Plugin release for **quotamon <version>**.

<the core release body, verbatim>

---
Core release: https://github.com/ubyjvovk/quota_monitor/releases/tag/v<version>
```

With the file absent, or present with an empty body:

```markdown
Plugin release for **quotamon <version>**.

Core release: https://github.com/ubyjvovk/quota_monitor/releases/tag/v<version>
```

`<version>` is `${GITHUB_REF_NAME#v}` — the same derivation the workflow's
existing "Verify tagged version" and "Package" steps already use.

**Step C — wire it in**

Add `body_path: release-body.md` to the existing `softprops/action-gh-release@v2`
step. Leave `files`, `generate_release_notes: true` and its `if:` condition as
they are. Do not touch the checkout, verify-tag, package or upload-artifact
steps.

Also make sure `release-body.md` and `core-release.json` cannot end up inside
the published zip: the Package step runs before these steps in file order but
**must** be ordered before them in execution too, or its `-x` list must exclude
them. State in your report which you relied on and why it holds.

## Out of scope
- `.github/workflows/release.yml` in the repository root (the main app release).
  It is correct and this ticket must not touch it.
- `scripts/release.sh`, `scripts/publish-omarchy-plugin.sh`, `VERSION`,
  `omarchy/manifest.json`, or anything that changes release *ordering*. The
  fallback exists precisely so ordering does not have to change.
- Any change to what the plugin zip contains, or to the tag-verification step.
- Adding a GitHub API call anywhere in the plugin's runtime (`Panel.qml`,
  `Model.js`, `fetch-quotamon.sh`). This is a build-time step in CI only; the
  panel deliberately performs no network version checks (T-0075).
- Making the plugin release fail, retry or wait when the core release is not yet
  published.
